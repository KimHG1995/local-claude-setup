# local-claude-setup

[한국어](README.md) | [English](README.en.md)

Claude Code를 쓸 때 필요한 규칙, 작업 흐름, 안전장치를 `.claude/` 아래에 정리해둔 **템플릿**이다. 이 저장소 자체는 돌아가는 프로젝트가 아니다. `.claude/`를 다른 프로젝트에 얹어서 쓰려고 만들었다.

아이디어는 두 군데에서 영향을 받았다.

- [ChrisWiles/claude-code-showcase](https://github.com/ChrisWiles/claude-code-showcase/tree/main/.claude) 에서 본 **모듈형 `.claude` 구조**
- [forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills) 에서 가져온 **LLM이 헛짚지 않게 만드는 작업 원칙**

그대로 가져다 쓴 건 아니고 내 작업 방식에 맞게 다시 풀었다. 그래서 "좋은 프롬프트 모음"이라기보다 **어디서 멈추고 무엇을 물어볼지 정해두는 운영 가이드**에 가깝다.

---

## 왜 만들었나

Claude Code를 계속 쓰다 보면 문제가 비슷하게 반복된다.

- 필요한 확인 없이 바로 구현에 들어감
- 수정 범위를 넘어서 주변 코드까지 건드림
- 검증 없이 "됐습니다" 하고 끝냄
- 프로젝트마다 자주 하는 리뷰, 계획, 마이그레이션 확인을 매번 다시 설명해야 함

프롬프트 한 줄로 해결하기보다 **역할별 파일로 나눠서 흐름을 잡아두는 방식**이 나한테는 더 잘 맞았다. 그래서 이건 프롬프트 중심이 아니라 워크플로우 중심이다.

---

## 어떻게 얹나

`.claude/`를 대상 프로젝트 루트에 복사하고, 아래를 그 프로젝트에 맞게 고친다. **안 쓰는 건 지운다.** 남겨두는 쪽이 기본값이 되면 금방 안 맞는 규칙 더미가 된다.

기존 `.claude/`가 있으면 먼저 비교하고 필요한 파일만 병합한다. 이 템플릿은 Bash, Git, `jq`, Python 3.9 이상을 사용하며 프로젝트 검사에는 Yarn과 `typecheck`/`test` 스크립트가 필요하다. 훅은 `${CLAUDE_PROJECT_DIR}`의 경로를 사용한다. 로컬 전용으로 운영하려면 대상 프로젝트에서 `.claude/` 제외 여부도 직접 설정한다.

공용 `AGENTS.md`를 쓰는 프로젝트는 루트 `CLAUDE.md`에서 `@AGENTS.md`로 가져온다. 문서 이름이나 우선순위를 적는 것만으로 자동 로드되지는 않는다. 설치 후 `/context`로 실제 로드 파일을, `/hooks`로 훅 연결을 확인한다.

### 반드시 고칠 것

| 파일 | 무엇을 고치나 |
| --- | --- |
| `CLAUDE.md` | 개인화 정보가 전부 플레이스홀더다. 담당자, 브랜치 패턴, 트래커 URL, 자주 쓰는 명령, 모듈별 주의사항을 채운다 |
| `skills/refactoring/references/*` | **아직 사내 전용 심볼이 28곳 남아 있다.** `@ApiEndpoint`, `@Standard*ValidationPipe`, `StandardErrorFilter`, `ResponseTransformInterceptor`, `buildPageData` 등은 NestJS 표준이 아니라 특정 코드베이스의 것이다. 그 프로젝트의 실제 데코레이터와 유틸로 바꾼다 |
| `rules/nestjs.md` | **통째로 예시다.** 얹을 프로젝트의 레이어 구조와 검증 수단으로 다시 쓴다 |
| `rules/code-quality.md` | `paths`를 그 프로젝트 확장자로. 지금은 `**/*.ts` |
| `hooks/*.sh` | 패키지 매니저와 명령. 지금은 `yarn typecheck`, `yarn test` |
| `settings.local.json` | 허용 명령. 필요한 것만 하나씩 연다 |
| `commands/*.md` | 티켓 표기와 경로. 지금은 `<TICKET>-1234`, `src/entities/` |
| `skills/commit-pr/` | **PR 이력 조회의 기본값은 GitHub + `gh`다.** 커밋 쪽은 Git만 쓰므로 호스트와 무관하다. GitLab, Bitbucket 등이면 스크립트의 gh 블록을 바꾸거나 `--convention FILE`로 규칙 파일을 넘긴다 |

`rules/minimal-coding.md`와 `rules/git.md`는 스택과 무관해서 대체로 그대로 간다.

### 그대로 가져갈 만한 것

규칙 문장보다 **배치 방식**이 이 저장소의 값이다.

1. 로드 시점으로 자리를 나누는 기준
2. 채택 기준 (A)/(B)와 「기본값은 삭제」
3. 스킬 골격: `SKILL.md`는 유형 판단만, 내용은 `references/`에
4. `rules-check`의 역할 정의: 고치지 않고, 버그도 찾지 않고, 인용 못 하면 버린다

## 구조

Claude Code는 프롬프트를 여러 자리에 둘 수 있고 자리마다 로드 시점이 다르다. 그 차이가 곧 배치 기준이다.

| 자리 | 언제 로드되나 | 무엇을 두나 |
| --- | --- | --- |
| `CLAUDE.md` | 매 세션 | 모든 세션에 참인 것. 금지, 확인 게이트, 개인 컨텍스트 |
| `rules/` (`paths` 없음) | 매 세션 | 파일 유형과 무관하게 늘 참인 판단 기준 |
| `rules/` (`paths` 있음) | 매칭 파일 `Read` 시 | 그 유형을 만질 때만 필요한 convention |
| `commands/` | `/명령어` 호출 시 | 반복 작업의 절차와 출력 형식 |
| `skills/` | 상황이 맞을 때 자동, 직접 호출도 가능 | 유형을 가르고 해당 참조만 여는 가이드 |
| `agents/` | subagent로 부를 때 | fresh context가 목적 자체인 절차 |

**상시 로드되는 자리는 분량 자체가 비용이다.** 그래서 `minimal-coding.md`와 `git.md`는 짧게 유지하고, 파일 유형에 딸린 convention은 `paths`를 걸어 내렸다. 코드를 쓰지 않는 세션이 훨씬 많다.

여기 함정이 하나 있다. **`paths` 게이트는 매칭 파일을 `Read` 도구로 읽을 때만 걸린다.** `Write`나 `Edit`으로는 안 걸리고 Bash로 읽어도 안 걸린다. 그래서 새 파일만 만드는 작업은 coding rules가 하나도 적용되지 않은 채 끝날 수 있다. 게다가 `paths`가 붙은 rules는 subagent에 상속되지 않아서, 코드를 쓰는 위임에는 위임문에 "이 rules 파일을 직접 Read하라"를 넣어야 한다.

## 스킬 골격

스킬은 전부 같은 모양이다.

```text
skills/<이름>/
├─ SKILL.md              ← 트리거 설명 + 유형 판단만
├─ references/
│  └─ <유형>.md           ← 생성 규칙, Anti-pattern, Template, Example, 검증
└─ scripts/
   └─ <검증>.sh
```

현재 셋이 들어 있다. 전부 예시로 봐도 된다.

- **`refactoring/`** — 요청, 응답 계약을 유지하는 정리(1단계)와 허용 입력, 형변환, 응답 등이 바뀌는 변경(2단계)을 가른다
- **`entity-migration/`** — Entity 변경을 위험도로 가른다. 컬럼 추가와 컬럼 삭제는 위험이 다르다
- **`commit-pr/`** — 명시된 컨벤션과 PR template을 우선하고, **해당 작업의 실제 이력으로 보완한다.** 근거가 부족한 미정 항목만 묻는다

유형별로 갈라두면 지금 필요한 참조 파일만 읽고 움직인다. 이 구조로 얻으려는 것은 자동 트리거와 명시적인 유형 판단이다. 토큰 절감 여부는 비교 기준과 실제로 읽은 참조에 따라 달라진다. 과거의 호출당 약 660토큰은 `o200k_base`로 계산한 특정 버전의 정적 추정치이며, Claude의 실측 토큰이나 청구 비용이 아니다.

**`SKILL.md` 본문은 `o200k_base` 기준 350토큰을 넘지 않는다.** 라우터가 담을 것은 유형 판단, 매번 필요한 출력 형식, 참조를 열기 전에 걸려야 하는 안전장치뿐이다. 측정 도구는 이 상한을 검사하고, `CLAUDE.md`, 상시 rules, 스킬 메타데이터, 호출 시 본문과 참조의 비용을 구분해 보여준다. 실제 런타임의 로드 여부와 비용은 `/context`와 사용량으로 별도 확인한다. [검증 명세](docs/validation-contract.md)에 범위와 실행 방법이 있다.

## 규칙을 어떤 기준으로 넣고 빼나

LLM 설정은 놔두면 계속 커진다. 500줄이 1000줄이 되고, 서로 충돌하는 지시가 생기고, 정작 중요한 규칙의 신호가 묻힌다. 그래서 늘리는 쪽이 아니라 **줄이는 쪽에 기본값을 뒀다.**

**기본값은 삭제다.** 근거가 불확실하면 보류하지 않고 뺀다. 둘 중 하나를 충족해야 넣는다.

- **(A) 모델이 원리적으로 알 수 없는 것** — 내 환경, 내 취향과 그 이유, 내 결정 이력. 실패 사례가 없어도 넣는다
- **(B) 모델 행동을 교정하고, 지금 모델에서 재현되는 실패가 근거로 있는 것** — "이 줄이 없어서 생긴 실패"를 사건으로 댈 수 있어야 한다

인정하지 않는 사유도 정해뒀다. "안전장치라서", "있으면 좋을 것 같다", "원문이 잘 쓰여 있다", "다른 줄이 이걸 참조한다". 마지막 건 참조하는 쪽이 먼저 채택돼야 성립한다.

결국 기준은 하나다. **이 줄을 지웠을 때 실제로 문제가 생기는가.**

**(B)의 모델 행동 검증은 얹은 쪽에서 한다.** 이 저장소의 훅과 스크립트는 여기서 회귀 테스트하지만, 프로젝트별 규칙의 효과는 대상 작업에서 확인한다. 같은 코드, 작업, 모델, 도구 설정에서 해당 규칙만 제거한 경우와 유지한 경우를 비교하고 여러 사례와 반복 실행의 실패율, 회귀를 기록한다. 한 번 실패가 나오지 않았다는 이유로 불필요하다고 결론내리지 않는다. `claude --safe-mode`는 스킬, 훅, MCP, 메모리 등도 함께 끄므로 전체 설정 문제 진단용이며, 한 규칙의 효과를 분리하는 대조군으로 쓰지 않는다.

무엇을 왜 넣고 뺐는지는 [`ADOPTED.md`](ADOPTED.md)에 적는다. 상시 로드도 아니고 `paths`가 걸린 것도 아니라 프롬프트를 고칠 때만 읽힌다. 따로 두는 이유는 **같은 규칙을 근거를 모른 채 되살리거나 다시 빼는 걸 막기 위해서**다.

### 스택에 묶지 않는다

규칙이 겨냥하는 관심사와 그걸 해결하는 도구를 분리한다.

`minimal-coding.md`는 "신뢰경계에서 입력을 검증한다"까지만 적고 라이브러리를 특정하지 않는다. 그 경계가 어디이고 무엇으로 검증하는지는 `nestjs.md`가 맡는다. 프로젝트를 옮기면 `nestjs.md`만 바뀌고 `minimal-coding.md`는 그대로 간다.

측정 수치도 남의 걸 받아 쓰지 않는다. "테스트당 mock 3개 이하" 같은 상한은 특정 저장소를 세서 나온 값이라 그대로 옮기면 근거가 없다. **자기 저장소를 같은 방식으로 세는 게 요지이지 그 숫자가 요지가 아니다.**

### 일부러 안 만든 것

프로세스를 다 갖추면 **AI 개발 프로세스를 관리하는 비용이 실제 개발 비용보다 커진다.** nullable 필드 하나 추가하는 데 계획부터 리뷰 수렴까지 전 흐름이 개입하면 곤란하다.

- 개발 파이프라인 스킬(plan → implement → review-loop → ship). 지금 셋이 실제 업무에서 안정적으로 도는 걸 본 다음에 붙인다
- `paths` 공백을 메우는 훅. 그로 인한 실패를 아직 관찰하지 못했다. 관찰되면 그때 넣는다

```text
.claude/
├─ CLAUDE.md                  ← 매 세션 상주. 금지와 확인 게이트
├─ rules/
│  ├─ minimal-coding.md       (상시)
│  ├─ git.md                  (상시)

├─ agents/
│  └─ rules-check.md          ← fresh context로 rules 대조
├─ commands/
│  ├─ commit.md
│  ├─ pr.md
│  ├─ pr-review.md
│  ├─ migration-check.md
│  └─ new-feature.md
├─ hooks/
│  ├─ common.sh               ← 입력, 저장소 탐색, JSON 피드백
│  ├─ pre-edit-branch-check.sh
│  ├─ post-edit-typecheck.sh
│  └─ post-edit-test.sh
├─ settings.local.json
└─ skills/
   ├─ refactoring/            (SKILL.md + references/ + scripts/)
   ├─ entity-migration/
   └─ commit-pr/

ADOPTED.md                    ← 무엇을 왜 넣고 뺐나
docs/validation-contract.md   ← 훅, 검사 도구의 입출력과 검증 범위
tests/                        ← 임시 저장소로 실행하는 회귀 테스트
tools/measure-skill-tokens.py ← 상시 지침 비용과 라우터 350토큰 상한 검사
```

## 정리

Claude Code를 더 똑똑하게 만드는 설정이 아니라 **덜 흔들리고 덜 실수하게 만드는 가이드 세트**에 가깝다.

좋은 답을 받는 것도 중요하지만 그보다 먼저,

- 함부로 가정하지 않게 하고
- 불필요한 곳까지 건드리지 않게 하고
- 검증 없는 완료 보고를 못 하게 하고
- 팀 컨텍스트를 무시한 "예쁜 정리"를 못 하게 하는 것

대충 이런 이유로 만들었다. 그대로 복사해 쓰라고 만든 게 아니니 자기 프로젝트에 맞게 고쳐서 쓰는 게 맞다.
