# local-claude-setup

[한국어](README.md) · [English](README.en.md)

로컬에서 Claude Code를 쓸 때 자주 필요한 규칙, 작업 흐름, 안전장치들을 `.claude/` 아래에 정리해둔 저장소

기본 아이디어는 두 군데에서 영향을 받았으며

- [ChrisWiles/claude-code-showcase](https://github.com/ChrisWiles/claude-code-showcase/tree/main/.claude) 에서 본 **모듈형 `.claude` 구조**
- [forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills) 에서 가져온 **LLM이 헛짚지 않게 만드는 작업 원칙**

다만 그대로 가져다 쓴 건 아니고, 내가 선호하는 작업 방식에 맞게 다시 풀어냈다. 그래서 이 저장소는 “좋은 프롬프트 모음”이라기보다 **Claude Code를 조금 더 일관되게 쓰기 위한 운영 가이드**에 가깝다.

---

## 왜 이렇게 구성했나

Claude Code를 계속 쓰다 보면 문제는 비슷하게 반복된다.

- 필요한 확인 없이 바로 구현에 들어감
- 수정 범위를 넘어서 주변 코드까지 건드림
- 검증 없이 "됐습니다" 하고 끝냄
- 프로젝트마다 자주 하는 리뷰/계획/마이그레이션 확인을 매번 다시 설명해야 함

나는 이걸 프롬프트 한 줄로 해결하기보다, **역할별 파일로 나눠서 흐름을 잡아두는 방식**이 더 잘 맞았다.

그래서 이 레포는 대략 아래 네 층으로 구성했다.

1. **로컬 운영 규칙** — 어떤 상황에서 멈추고, 무엇을 물어보고, 무엇을 금지할지
2. **작업 단위 명령어** — 커밋, PR 리뷰, 신규 기능 계획, 마이그레이션 체크
3. **판단 가이드** — 특히 리팩토링처럼 "어디까지가 안전한가"를 나누는 기준
4. **자동 안전장치** — 보호 브랜치 차단, 타입체크/테스트 자동 실행

## 아키텍처

### 1. `.claude/CLAUDE.md`

이 레이어는 공용 `AGENTS.md`, 루트 `CLAUDE.md` 위에 덧붙는 **로컬 운영 매뉴얼**이다.

여기서 하는 일은 크게 세 가지다.

- 어떤 작업은 반드시 먼저 확인받도록 강제
- 어떤 작업은 명시적 요청 없이는 하지 않도록 제한
- 수정 후 어떤 검증을 기본으로 돌릴지 정함

즉, AI에게 "알아서 잘 해봐"라고 맡기는 문서라기보다, **작업 전에 한 번 더 멈추게 만드는 브레이크와 가드레일**에 가깝다.

---

### 2. `.claude/commands/`

반복되는 작업은 슬래시 커맨드 단위로 분리해뒀다.

- `new-feature.md` — 기능 구현 전에 모듈 구조를 읽고, 구현 순서를 먼저 제안하게 함
- `commit.md` — 스테이징된 변경을 분석해서 커밋 메시지를 초안하게 함 (판단 규칙은 `commit-pr` 스킬을 따름)
- `pr.md` — 현재 브랜치 커밋으로 draft PR을 만들게 함, Jira 티켓·커밋 목록·수정내역까지 본문에 채움 (판단 규칙은 `commit-pr` 스킬을 따름)
- `pr-review.md` — 현재 브랜치 변경을 아키텍처 체크리스트 기준으로 검토하게 함
- `migration-check.md` — Entity 변경이 실제 마이그레이션이 필요한 변경인지 보고만 하게 함

핵심은 "무언가를 바로 수행"하게 만드는 것보다 **판단 순서와 출력 형식을 어느 정도 고정**하는 데 있다.

예를 들어 `/new-feature`는 곧바로 코드를 쓰게 하지 않고,

1. 모르는 컨텍스트를 먼저 질문하고
2. 대상 모듈 구조를 읽고
3. 커밋 분리 기준까지 포함한 구현 순서를 제안한 뒤
4. 확인을 받고 나서 시작하게 만든다.

속도도 중요하지만, 나는 그보다 **예측 가능한 작업 흐름**을 더 중요하게 보는 편이라 이렇게 구성했다.

### 3. `.claude/skills/`

여기는 커맨드라기보다 **작업 판단 기준을 담은, 유형별로만 필요한 만큼 불러 쓰는 가이드**다. 왜 이 모양으로 짰는지는 아래 "스킬 구조를 어떻게 다시 짰나" 절에 따로 정리했다.

모든 스킬은 같은 골격을 쓴다.

```text
skills/<이름>/
├─ SKILL.md              ← 트리거 설명 + 유형 판단만 (내용은 안 담음)
├─ references/
│  └─ <유형>.md           ← 생성 규칙 + Anti-pattern + Template + Example
└─ scripts/
   └─ <검증>.sh
```

현재 스킬은 셋이다.

- **`refactoring/`** — 리팩토링을 두 단계로 나눈다.
  - `references/phase1-safe-changes.md` — 프론트엔드 영향 없이 바로 적용 가능한 변경 (DTO 분리, Swagger 정리, 기존 검증의 class-validator 이동)
  - `references/phase2-contract-changes.md` — 프론트 협의가 필요한 응답 구조 표준화 (Filter / Interceptor / wrapped / paged 응답)
  - `scripts/validate.sh` — typecheck → (선택) 모듈 테스트 → lint
- **`entity-migration/`** — Entity 변경을 위험도별로 나눈다.
  - `references/add-column.md` / `drop-or-type-change.md` / `relation-and-index.md`
  - `scripts/check-entity-diff.sh` — `src/entities/` diff에서 컬럼·관계·인덱스 변경 후보를 휴리스틱으로 뽑아 보여줌
- **`commit-pr/`** — 커밋 메시지와 PR 본문, 두 상황으로 나눈다.
  - `references/commit-message.md` — 타입·스코프 판단, 분리 여부, 영어 설명 규칙 (Step 1~6 절차)
  - `references/pr-description.md` — Jira 티켓 연동, 커밋 목록, 수정내역을 담은 draft PR 작성 규칙
  - `scripts/collect-pr-context.sh` — 브랜치·티켓 번호·커밋 목록·변경 파일 통계를 한 번에 수집

리팩토링을 두 단계로 나눈 이유는 단순하다. "리팩토링"이라는 이름으로 한 번에 밀어붙이면, 실제로는 "안전한 정리"와 "계약 변경"이 쉽게 뒤섞인다. Entity 변경도 마찬가지다 — 컬럼 추가와 컬럼 삭제·타입 변경은 위험도 자체가 다르다. `commit-pr`은 결이 좀 다르다 — 유형별 위험도가 아니라 **작업 단계**(커밋 vs PR)로 가른 경우다. 유형별로 갈라두면 AI도 **수정 범위를 괜히 키우지 않고**, 지금 상황에 필요한 참조 파일 하나만 읽고 움직인다.

---

### 4. `.claude/hooks/`

여기는 말 그대로 **자동 안전장치**다.

- `pre-edit-branch-check.sh`
  - `main`, `master` 브랜치에서 직접 편집 차단
- `post-edit-typecheck.sh`
  - `.ts` 파일 수정 후 `yarn typecheck` 자동 실행
- `post-edit-test.sh`
  - `.spec.ts` 수정 후 해당 테스트 자동 실행

즉, "규칙을 적어두는 것"에서 끝내지 않고, 최소한의 검증은 **편집 직후 바로 반응**하도록 연결해뒀다.

---

### 5. `.claude/settings.local.json`

이 파일은 위 구조를 실제로 작동시키는 실행 설정이다.

- 허용할 명령을 최소 범위로 제한
- Edit/Write 전후 훅 연결
- 로컬 작업에서 자주 쓰는 검증만 열어둠

이 파일도 단순 설정 파일이라기보다, **"AI가 어디까지 자동으로 움직여도 되는가"를 정하는 정책 파일**에 가깝다.

## 스킬 구조를 어떻게 다시 짰나 (+ 실측)

전에는 `skills/refactoring-phase1.md`, `refactoring-phase2.md`처럼 파일을 그냥 나열해뒀다. 스킬을 더 늘리려고 보니 걸리는 게 있었다. **실제 Claude Code Skill이 아니었다** — `name`/`description` frontmatter를 가진 `SKILL.md`가 아니라 그냥 마크다운 문서였다. 그래서 "1단계 리팩토링 가이드 참고해서 진행해줘"처럼 내가 직접 이름을 불러줘야만 작동했고, 관련 상황이 와도 스스로 트리거되지 않았다.

그래서 Claude Code Skills가 원래 지원하는 3단계 로딩 구조를 따르기로 했다.

1. **메타데이터(`name` + `description`)** — 항상 상주. 이걸로 Claude가 "지금 이 스킬이 필요한가"를 판단한다.
2. **`SKILL.md` 본문** — 트리거될 때만 로딩. 유형 판단 기준만 두고 무거운 내용은 넣지 않는다.
3. **`references/*.md`** — 유형이 정해진 다음 그 파일 **하나만** 읽는다.

### 실제로 재봤더니

처음엔 "토큰 최적화"라고 적었는데, 재보니 **그 표현은 틀렸다.** 재현 스크립트를 레포에 넣어뒀다.

```bash
python3 tools/measure-skill-tokens.py
```

측정 결과 (tiktoken `o200k_base` 기준, Claude 토크나이저 근사치):

| 스킬 | 상주(frontmatter) | 라우터(SKILL.md 본문) | 호출당 오버헤드 |
| --- | ---: | ---: | ---: |
| `commit-pr` | 117 | 198 | +556 |
| `refactoring` | 131 | 270 | +628 |
| `entity-migration` | 110 | 334 | +692 |

**즉 이 구조는 토큰을 아끼지 않는다. 호출 1회당 평균 625 토큰을 더 쓴다.**

내가 처음에 착각한 이유는, 구버전을 "한 파일에 전 유형이 든 flat 파일"로 놓고 비교했기 때문이다. 그런 파일은 이 레포에 존재한 적이 없다. `refactoring-phase1.md` / `phase2.md`는 **이미 유형별로 갈라져 있었고**, 사용자가 이름을 불러서 하나만 로딩했다. 구버전도 이미 progressive였다 — 라우팅을 사람이 했을 뿐이다.

그래서 진짜 차이는 "유형을 갈랐나"가 아니라 **"라우팅을 사람이 하나 모델이 하나"**이고, 그 값이 호출당 625 토큰이다. 이걸로 사는 것은:

- **자동 트리거** — 파일명을 몰라도 된다
- **유형 판단을 모델이 함** — 구버전은 내가 1단계/2단계를 직접 골라야 했다. 잘못 고르면 그대로 잘못된 가이드로 진행된다
- **판단 기준이 파일로 명시되어 버전 관리됨**

세 번째 항목이 실질적으로 제일 크다. 2단계 변경(응답 계약이 바뀌는 변경)을 1단계 가이드로 진행하면 프론트가 깨진다. 그 사고 한 번 값이 토큰 625 × 호출 횟수보다 훨씬 비싸다. 상주 358 토큰은 200k 컨텍스트의 0.18%라 사실상 무시할 수준이고, 시스템 프롬프트라 캐시된다.

### 라우터 비만이 진짜 문제였다

재구성 직후 라우터가 **610 / 580 / 365** 토큰이었다. 라우팅과 무관한 내용(검증 절차, 완료 후 보고 규칙, 공통 규칙 설명)이 SKILL.md에 그대로 있었고, 특히 `refactoring/SKILL.md`의 검증 절은 두 참조 파일에 **이미 똑같이 들어있는 순수 중복**이었다.

그걸 references로 내려서 **198 / 270 / 334**로 줄였다. 라우터가 정당하게 담는 건 세 가지뿐이다 — 유형 판단 로직, 유형과 무관하게 매번 필요한 출력 형식, 참조를 열기 전에 걸려야 하는 안전장치. 측정 스크립트는 라우터가 350을 넘으면 실패한다. 다시 불어나는 걸 잡으려는 것이다.

여전히 유효한 것도 있다. **유형을 추가하는 비용은 거의 없다** — 판단 목록에 한 줄(약 12토큰) 추가가 전부다. 구버전 방식은 토큰은 안 늘지만 사용자가 외워야 할 파일명이 늘고, 옳게 고를 확률이 떨어진다.

반대로 `.claude/commands/`는 손대지 않았다. 커맨드는 원래도 `/명령어`로 명시적으로 불러야만 로딩되는 구조라 이미 lazy-load다. 여기에 SKILL.md 패턴을 얹을 이유가 없었다.

각 `references/*.md`는 전부 같은 순서로 통일했다 — **생성 규칙 → Anti-pattern → Template → Example → 검증**. 규칙만 있으면 "왜 안 되는지"가 빠지고, 예시만 있으면 "다른 케이스엔 어떻게 적용하는지"가 빠진다. 이 다섯을 한 세트로 묶어야 참조 파일 하나만 읽어도 판단부터 구현, 검증까지 끝난다. 검증은 사람이 실행 결과를 다시 설명할 필요 없게, 실제로 돌아가는 스크립트(`scripts/*.sh`)로 만들어뒀다.

스킬을 만드는 방식 자체(frontmatter는 `name`/`description`뿐, description이 곧 트리거니까 실제로 쓸 표현을 그대로 적는다, 다음 스킬로 넘기는 건 본문에 이름만 적으면 된다)는 Anthropic의 `skill-creator` 컨벤션을 따랐다.

> 참고로 개인 설계 메모 `claude-code-orchestration.md`에는 이보다 큰 그림 — plan → auto → ship → review 스킬 체인으로 계획 확정부터 draft PR까지 자율로 진행하는 구조 — 가 정리돼 있다. 이번엔 그 메모에서 **스킬을 어떻게 짜야 하는지에 대한 컨벤션만** 가져왔고, 체인 자체는 아직 옮기지 않았다. 세션 Task 목록 연동, 승인 게이트, 서브에이전트 위임 규율까지 들어가는 더 큰 작업이라 별도로 다룰 만하다고 봤다.

### 새 스킬을 추가한다면

이 골격을 그대로 복사해서 채우면 된다.

1. `SKILL.md` 작성 — `description`에 실제로 쓸 트리거 표현을 넣고, 본문엔 유형 판단 표만 둔다.
2. 유형별로 `references/<유형>.md`를 하나씩 — 생성 규칙 / Anti-pattern / Template / Example / 검증.
3. 필요하면 `scripts/`에 검증 스크립트를 추가한다.
4. 기존 커맨드가 같은 판단 기준을 쓰고 있었다면, 표를 복사하지 말고 스킬 쪽을 가리키게 바꾼다 (`migration-check.md`에 적용한 방식 — 같은 표가 두 곳에 있으면 둘 중 하나는 반드시 낡는다).

## 이 저장소가 가진 성격

이 레포는 흔한 템플릿 저장소와는 조금 결이 다르다.

나는 Claude에게 만능 프롬프트 하나를 주기보다,

- **행동 원칙은 `CLAUDE.md`에**
- **반복 작업은 `commands/`에**
- **세부 판단 기준은 `skills/`에**
- **실수 방지는 `hooks/`에**

이걸 나눠서 넣는 쪽을 더 선호한다.

그래서 아키텍처 자체도 **프롬프트 중심**이라기보다 **워크플로우 중심**에 가깝다.

영향을 받은 두 레퍼런스를 정리하면 대충 이렇다.

- `claude-code-showcase` 에서 가져온 것
  - `.claude/`를 역할별 폴더로 나누는 방식
  - commands / skills / hooks / settings 같은 분리된 운영 구조
- `andrej-karpathy-skills` 에서 가져온 것
  - AI가 성급하게 가정하지 않도록 만드는 원칙 중심 사고
  - 단순 구현보다 확인, 범위 제한, 검증 기준을 앞세우는 태도

그리고 여기에 내가 덧붙인 건 이런 부분들이다.

- 한국어 기준의 작업 문맥
- 백엔드 작업에 맞춘 예시와 흐름
- 마이그레이션, DTO, Mapper, 응답 형식, 브랜치 규칙 같은 실무형 체크포인트
- "무조건 자동화"보다 "어디서 멈춰야 하는지"를 분명히 하는 쪽에 더 초점

## 어떻게 쓰는가

사용 흐름은 대체로 이렇다.

### 1. 기본 규칙은 `.claude/CLAUDE.md`가 잡는다

작업 시작 전:

- 무엇을 먼저 물어봐야 하는지
- 어디까지 수정해도 되는지
- 무엇은 금지인지

이 기준을 이 파일이 먼저 잡아준다.

### 2. 반복 작업은 슬래시 커맨드로 호출한다

예시:

- `/new-feature` — 기능 추가 전 계획부터 세우기
- `/migration-check` — Entity 변경이 마이그레이션 대상인지 판단하기
- `/pr-review` — 현재 브랜치 전체를 체크리스트로 리뷰하기
- `/commit` — 스테이징된 변경을 분석해 커밋 메시지 만들기
- `/pr` — 현재 브랜치 커밋으로 draft PR 열기 (Jira 티켓·커밋 목록·수정내역 포함)

### 3. 스킬은 알아서 트리거되거나, 직접 불러서 쓴다

`skills/`는 실제 Claude Code Skill이라 `description`에 걸리는 상황(리팩토링, Entity 수정 등)이면 따로 부르지 않아도 스스로 트리거된다. 물론 명시적으로 불러도 된다:

- "1단계 리팩토링 기준으로 진행해줘"
- "2단계 리팩토링 기준으로 응답 구조까지 정리해줘"
- "이 Entity 변경, 마이그레이션 필요한지 봐줘" (Entity 파일을 건드리면 이 말 없이도 `entity-migration`이 먼저 반응한다)

즉, `skills/`는 명령어라기보다 **판단 모드를 바꾸는 가이드**다. 다만 `/명령어`처럼 매번 이름을 불러야 하는 건 아니라는 점이 커맨드와 다르다.

### 4. 수정 뒤에는 훅이 최소 검증을 자동으로 건다

- TS 파일을 고치면 타입체크
- 테스트 파일을 고치면 해당 테스트 실행
- 보호 브랜치면 편집 자체 차단

이렇게 해두면 사람이 매번 "타입 체크 돌렸어?" 같은 걸 다시 확인하지 않아도 된다.

## 내가 중요하게 보는 원칙

결국 이 저장소는 아래 원칙을 실제 작업 흐름으로 옮기려고 만든 것이다.

1. **모르면 먼저 물어본다**
2. **작업 범위를 넘어서 건드리지 않는다**
3. **구현보다 계획과 검증을 먼저 둔다**
4. **안전한 변경과 계약 변경을 분리한다**
5. **로컬 워크플로우를 문서가 아니라 동작으로 고정한다**

이 원칙은 `andrej-karpathy-skills` 쪽에서 받은 문제의식과 닿아 있고, 구조적인 배치는 `claude-code-showcase` 쪽에서 많이 힌트를 얻었다. 다만 결과물은 결국 **내 식으로 다시 조립한 로컬 가이드 세트**에 가깝다.

## 정리

이 저장소는 Claude Code를 더 똑똑하게 만드는 설정이라기보다, **작업할 때 덜 흔들리고 덜 실수하게 만드는 가이드 세트**에 가깝다.

좋은 답을 하게 만드는 것도 중요하지만, 그보다 먼저:

- 함부로 가정하지 않게 하고
- 불필요한 곳까지 건드리지 않게 하고
- 검증 없는 완료 보고를 못 하게 하고
- 팀 컨텍스트를 무시한 "예쁜 정리"를 못 하게 하는 것

대충 이런 이유로 이 구조를 만들었다.
