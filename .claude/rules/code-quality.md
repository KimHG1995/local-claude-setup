# 코드와 테스트 품질

`paths`가 걸려 있어 `.ts` 파일을 **Read 도구로 읽을 때만** 로드된다. `Write`, `Edit`, Bash `cat`으로는 로드되지 않는다. 새 파일만 만드는 작업에서는 이 파일이 적용되지 않은 채 끝나므로, 코드를 쓰는 위임에는 위임문에 "이 파일을 직접 Read하라"를 넣는다. `paths`가 붙은 rules는 subagent에 상속되지 않는다.

## 테스트가 동어반복이 되지 않게 한다

가장 자주 새는 자리다. **actual은 대상 함수의 output이고, expected는 독립으로 하드코딩한 리터럴이다.**

expected를 복제하거나 변형해서 actual을 만들면 대상 함수가 비교 경로에서 빠져 테스트가 아무것도 검증하지 않는다.

```ts
// ❌ 대상 함수가 비교에서 빠졌다. 무엇을 바꿔도 통과한다.
const expected = buildLabel(input);
expect(buildLabel(input)).toBe(expected);

// ❌ expected를 대상 함수의 로직으로 만들었다. 같은 문제다.
const expected = `${input.name} (${input.count}건)`;
expect(buildLabel(input)).toBe(expected);

// ✅ expected는 손으로 적은 리터럴이다.
expect(buildLabel({ name: '홍길동', count: 3 })).toBe('홍길동 (3건)');
```

**구현을 먼저 쓰고 그 구현에 맞춰 테스트를 쓰면 테스트가 명세가 아니라 현재 구현의 복사본이 된다.** 기대 입출력은 구현 전에 정한다.

## 로직을 검증 가능한 단위로 쓴다

유닛 테스트 전수 통과만으로 핵심 동작을 신뢰하려면 로직이 그렇게 통과할 수 있는 모양이어야 한다.

계산은 순수 함수로 두고 I/O(DB, 네트워크, 파일, 시간)는 함수 시그니처의 명시적 파라미터로 밀어낸다. 그러면 각 함수가 `입력 → 출력`으로 검증되고, 그 작은 검증들이 이어져 전체 흐름을 보증한다.

**계산과 I/O가 한 함수에 얽혀 mock 없이는 테스트할 수 없어지는 지점이 분해 신호다.** 이때 순수 계산을 별도 함수로 빼는 것은 [`minimal-coding.md`](minimal-coding.md)의 단일 호출부 helper 금지에 걸리지 않는다. 호출부가 하나여도 그 분해가 mock 없이 실제 값으로 검증되는 경계를 만들면, 이름을 붙이려는 추출이 아니라 검증을 위한 구조이기 때문이다. 그 경계가 생기지 않는 분해는 이 예외가 아니다.

**한 테스트에 mock이 여러 개 필요하면 테스트가 아니라 대상 함수를 고친다.** mock 개수는 그 함수가 쓰는 외부 의존성 개수를 그대로 보여 준다. mock이 많은 것은 원인이 아니라 결과다.

> 여기에 "mock 3개 이하" 같은 상한을 두지 않는 것은 의도다. 그런 숫자는 특정 저장소를 세서 나오는 값이라 근거 없이 옮기면 임의의 기준이 된다. 이 저장소의 테스트를 직접 세기 전까지는 숫자 없이 위 신호만 쓴다.

## 주석

- 코드가 이미 말하는 내용을 되풀이하지 않는다. 지우면 실패를 막기 어려워지는 것만 남긴다.
- JSDoc은 Controller와 Service의 public 메서드에만 붙인다. 메서드명이 이미 말하는 내용("~를 조회한다")을 반복하지 않고, 비자명한 제약, 부작용, 정책만 적는다.
- Repository 메서드에는 JSDoc을 붙이지 않는다.

## 타입

- 신규 `any` 도입을 지양한다. 이미 있는 것은 건드리지 않는다.
- `@ts-ignore`, `@ts-expect-error`를 새로 추가하지 않는다.
- 저장소에 없던 새 용어를 만들어 쓰지 않는다. 기존 이름을 grep해서 확인한다.
