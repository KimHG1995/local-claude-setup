# refactoring

## 이 스킬이 하는 일

모듈을 고치면서 "안전하게 바로 적용 가능한 정리"와 "API 계약이 바뀌는 변경"을 섞지 않도록 유형을 먼저 가른다.
유형이 정해지면 아래 표에서 **해당 reference 하나만** 읽는다 — 둘 다 미리 읽지 않는다. 지금 필요 없는 유형의 템플릿·예시까지 컨텍스트에 올릴 이유가 없다.

## 유형 판단

아래 질문 중 하나라도 "예"면 **2단계**다.

- 응답 body의 필드·구조·래핑이 바뀌는가? (`success`/`data`/`meta` 래핑, 페이지네이션 형식 변경 등)
- 에러 응답 형식이 바뀌는가? (`StandardErrorFilter` 적용 등)
- 이 API를 쓰는 프론트/모바일 클라이언트 코드가 함께 바뀌어야 하는가?

전부 "아니오"면 **1단계**다.

| 유형 | 참조 파일 | 프론트 영향 |
| --- | --- | --- |
| 1단계 — 안전한 정리 | [`references/phase1-safe-changes.md`](references/phase1-safe-changes.md) | 없음 |
| 2단계 — 계약 변경 | [`references/phase2-contract-changes.md`](references/phase2-contract-changes.md) | 있음, 사전 협의 필수 |

판단이 애매하면 넘겨짚지 말고 사용자에게 확인한 뒤 진행한다.

## 공통 규칙

- **전면 리팩토링 금지.** 수정 대상 모듈/API 범위 안에서만 적용한다.
- 이 스킬은 기능 구현·버그 수정과 **함께 자연스럽게** 적용하는 것이지, 리팩토링 자체가 목적인 별도 작업을 임의로 새로 벌이지 않는다. 범위를 넓히고 싶으면 먼저 확인받는다.
- 같은 모듈에 1단계·2단계 대상이 섞여 있으면, 이번 변경에는 1단계만 적용하고 2단계 대상은 "다음에 프론트 협의 후 진행" 항목으로 보고만 한다.

## 검증

변경 후에는 참조 문서가 안내하는 검증 스크립트를 실행한다.

```bash
bash .claude/skills/refactoring/scripts/validate.sh <module-path>
```

`<module-path>`는 생략 가능하다 — 생략하면 typecheck·lint만 돈다.

## 완료 후

어떤 유형을 적용했는지, 검증 스크립트 결과를 한 줄로 요약해 보고한다. 2단계 대상을 발견했지만 이번엔 적용하지 않았다면 그것도 함께 알린다.
