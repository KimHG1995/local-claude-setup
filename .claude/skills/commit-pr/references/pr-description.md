# PR 생성

`commit-pr` 스킬에서 "브랜치 변경사항을 PR로 올리는 상황"으로 판단됐을 때만 읽는다.

## 섹션 구성을 어디서 정하는가

**이 파일은 섹션 구성을 정의하지 않는다.** 아래 순서로 정한다.

1. **사용자가 지정했거나 저장소에 명시된 PR 규칙**을 우선한다. 이미 정한 내용은 이력이 없어도 다시 묻지 않는다.
2. **PR template** (`.github/pull_request_template.md` 또는 `.github/PULL_REQUEST_TEMPLATE.md`)의 구성을 따른다. 별도 형식을 만들지 않는다.
3. 부족한 부분만 **실제 PR 본문**에서 관찰한다. 제목이나 커밋 언어로 본문 구성, 언어를 추정하지 않는다.
4. 남은 미정 항목만 사용자에게 묻는다. 「기본 구성」은 후보로 제시한다.

```bash
bash .claude/skills/commit-pr/scripts/derive-git-convention.sh --mode pr 5
```

exit `0`은 template/선택한 규칙 또는 본문 자료 확보를 뜻하며 모든 항목이 확정됐다는 뜻은 아니다. `2`는 본문 근거 부족, `1`은 조회/입력 실패다. 조회 실패는 PR 없음이 아니다. template이나 명시된 규칙으로 해결된 항목은 어느 코드에서도 되묻지 않는다. 상세 옵션: [helper 계약](helper-contract.md).

## 항상 적용하는 것

아래는 프로젝트 convention이 달리 정해도 계속 적용한다. 섹션 이름이 무엇이든 내용이 이 조건을 만족해야 한다.

- **개요는 사용자가 관찰할 수 있는 행동으로 문제를 정의한다.** "언제, 어떤 동작이 잘못 일어났는가"로 시작한다. "회귀", "single source of truth" 같은 내부 용어로 시작하지 않는다. 메인 변경 2~3개만 적고, 메커니즘 세부와 부수 수정은 아래 섹션이나 커밋 로그로 내린다.
- **Before와 After는 같은 범위에서 1:1로 대응하는 것만 넣는다.** After에 대응이 없는 Before 세부는 뺀다. 한쪽은 전체 객체, 다른 쪽은 그 안의 필드 하나처럼 레벨을 섞지 않는다.
- **검증한 사실만 쓴다.** 확인하지 못한 것은 "미확인"으로 명시한다. 추정을 사실처럼 쓰지 않는다.
- **리뷰 결과를 동작 확인의 근거로 쓰지 않는다.** "리뷰에서 지적 없음", "독립 검토 통과"를 테스트나 검증 항목에 적지 않는다. 그 자리에는 실행한 명령과 관찰한 출력만 적는다. 리뷰는 결함을 찾는 수단이지 동작을 확인하는 수단이 아니다.
- **커밋을 빠짐없이 나열한다.** "총 N개 파일 변경"으로 뭉뚱그리지 않는다.
- **수정내역은 `git diff --stat` 출력을 붙여넣는 것이 아니다.** 파일이나 모듈 단위로 사람이 읽을 수 있게 요약한다.

## 절차

### 1. 재료 수집

```bash
bash .claude/skills/commit-pr/scripts/derive-git-convention.sh --mode pr 5
```

이 스크립트는 PR template 또는 PR 제목, 본문을 수집한다. 브랜치와 티켓은 현재 요청 및 `git branch --show-current`로 별도 확인한다. base 확인 후 `git log <base>..HEAD`로 PR에 포함될 커밋 목록을 수집한다. template/명시된 규칙이 있으면 이력 조회는 필요하지 않다.

### 2. base 확인

base를 임의로 `main`으로 잡지 않는다. Phase를 쌓는 구조면 base가 직전 Phase 브랜치일 수 있다. 확실하지 않으면 묻는다.

### 3. diff 점검

```bash
git diff <base>...HEAD --stat
```

- 의도 밖 변경이 섞였는지 확인한다. 있으면 분리하거나 확인받는다.
- **삭제된 줄만 따로 모아 한 번 더 본다.** 각 삭제가 요청 범위 안인지, 그 코드를 부르던 곳이 남아 있는지 확인한다. 추가된 줄은 읽히지만 삭제된 줄은 훑을 때 눈에 걸리지 않는다.
- 주석과 공백을 뺀 실제 코드 줄 수가 **300~400줄**을 넘으면 **PR을 나누는 구체안을 먼저 제시하고 사용자 결정을 받는다.** 어느 커밋을 어느 PR로 보낼지 적는다. 사유만 적고 넘어가면 제한이 작동하지 않는다. 테스트 코드를 포함해서 센다.

### 4. rules 대조

diff에 코드 파일이 있으면 `rules-check` agent를 부른다. 대상 diff와 기준 branch를 지정한다. 대조하지 못한 파일이 있다고 답하면 그 이름과 사유를 PR 본문에 「미확인」으로 명시한다.

찾은 내용은 사용자에게 제시하고, 채택된 것만 반영한다. 반영해서 diff가 바뀌면 3번부터 다시 한다.

### 5. Jira 티켓

티켓 번호가 있으면 배경을 정리한다.

- Jira 연동 도구가 이 세션에 연결돼 있으면 그것으로 제목과 요약을 가져온다.
- 연결돼 있지 않으면 사용자에게 요약을 물어보거나, 티켓 번호만 남긴다.
- **존재를 확인하지 못한 링크를 지어내지 않는다.** 조회에 실패했으면 "링크 확인 필요"로 적는다.
- `CLAUDE.md` 개인화 정보에 Jira base URL이 채워져 있으면 `<base URL>/browse/<티켓>` 형태로 만든다.

### 6. 초안 제시 후 생성

완성된 본문을 보여 주고 확인받는다. 확인되면 실행한다.

```bash
gh pr create --draft --assignee @me --base <base> --title "<제목>" --body "<본문>"
```

**항상 draft로 열고 assignee는 본인으로 둔다.** Open으로 바꾸는 것은 사용자가 `gh pr ready`로 한다. PR 생성은 [`git.md`](../../../rules/git.md)의 승인 게이트 대상이다.

### 7. 마무리 보고

PR URL을 보고한다. 그리고 **"Open으로 올리기 전에 실제 동작을 직접 확인해야 한다"를 한 문장으로 알린다.** 자동 테스트와 빌드 통과는 실제 동작 확인이 아니다. 미확인 항목이 있으면 그 목록을 직접 확인 대상으로 함께 제시한다.

## 기본 구성

template도 기존 PR도 없을 때 **후보로 제시할** 구성이다. 확인 없이 쓰지 않는다.

```markdown
## 배경
- [<티켓>](<링크>) — <티켓 제목>
- <왜 이 변경이 필요한가 1~2줄>

## 변경 사항
- <모듈 단위 요약 1>
- <모듈 단위 요약 2>

## 커밋
| Commit | 설명 |
| --- | --- |
| `<sha>` | `<제목>` |

## 검증
- 실행한 명령과 관찰한 출력
- 미확인 항목이 있으면 여기에 명시
```

## Anti-pattern

- ❌ **template이 있는데 자기 형식으로 쓰는 것.** template이 최우선이다.
- ❌ 명시된 규칙과 template도 없는 저장소에서 본문 이력 없이 형식을 확정하는 것. 남은 미정 항목만 확인한다.
- ❌ 존재를 확인하지 못한 Jira 링크를 만들어 넣는 것.
- ❌ `git diff --stat` 출력을 그대로 붙여넣고 "수정내역"이라 부르는 것.
- ❌ "리뷰 통과"를 검증 섹션에 적는 것.
- ❌ 확인 없이 Open 상태로 PR을 여는 것.
- ❌ base를 확인하지 않고 항상 `main`으로 잡는 것.

## 검증

- [ ] template이 있으면 그 구성을 따랐는가?
- [ ] 명시된 규칙, template, 본문 이력으로도 정해지지 않은 항목만 확인했는가?
- [ ] 커밋이 빠짐없이 나열됐는가?
- [ ] 검증 섹션에 실행한 명령과 출력만 있는가? 리뷰 결과가 섞이지 않았는가?
- [ ] 미확인 항목이 "미확인"으로 명시됐는가?
- [ ] draft로 열렸는가?
