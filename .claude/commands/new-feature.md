새 기능 구현 전 현재 모듈 구조를 파악하고 작업 계획을 제안하라.

## Step 1 — 컨텍스트 파악

사용자에게 아직 모르는 정보가 있으면 먼저 물어본다:

- 어떤 모듈에 추가하는가?
- KDS 티켓 번호가 있는가?
- Entity 변경이 포함되는가?

## Step 2 — 대상 모듈 현황 분석

대상 모듈 디렉토리를 읽고 아래를 파악한다:

1. Controller — 현재 엔드포인트 목록, 데코레이터 패턴
2. Service — 메서드 목록, 의존성
3. Repository — 쿼리 패턴
4. DTO 구조 — shared/endpoints 분리 여부, barrel export 여부
5. Mapper 존재 여부

## Step 3 — 작업 계획 제안

아래 형식으로 제안한다:

### 구현 순서 (커밋 분리 기준)

1. **[Entity 변경]** (해당 시) — 파일럿이 마이그레이션 진행
2. **[DTO 추가]** — request/response DTO 신규 파일
3. **[Repository 메서드 추가]** — Entity 기반 반환
4. **[Service 메서드 추가]** — 정책 결정 + Mapper 호출
5. **[Controller 엔드포인트 추가]** — HTTP 레이어만
6. **[테스트]** (기존 테스트가 있는 경우)

### 리팩토링 단계 판단

- 해당 모듈이 이미 DTO/Mapper 패턴을 쓰고 있는가?
  - 예 → 동일 패턴 유지
  - 아니오 → 1단계 리팩토링 병행 여부 사용자에게 확인

### 주의사항 (해당 모듈별)

`alimtalk` 관련이면: v1/v2 모두 영향 범위 확인
`reservation-date` 관련이면: 트랜잭션 처리 필요 여부 확인
`access`/`attendance` 관련이면: 데드락 방지 잠금 순서 유지 확인
`entities` 변경 포함이면: Entity 변경 내용을 /migration-check 로 보고

## Step 4 — 확인 후 구현 시작

계획을 제안한 뒤 "이 순서로 진행할까요?" 확인을 받고 구현을 시작한다.
확인 없이 바로 코드를 작성하지 않는다.
